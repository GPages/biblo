# Biblo: project brief and handoff

Put this file at the repo root. It is the full context from the design session in Claude.ai.

## What it is

Offline Windows desktop app for a small primary school library: track books, track pupils, record who borrowed which book and when. Open source (0BSD), no profit. **Nobody can maintain it on site**, so it must be as simple and robust as possible. Priorities: readability, simplicity, speed. UI text is **French**; code identifiers and comments are **English** (the user-facing error messages in `error.rs` are French on purpose).

Target: Windows 10 PC (may move to 11), no internet. Developer machine: Ubuntu 24.04 (must be able to run and test the app there, and ideally cross-compile the Windows .exe).

## Functional spec (from the user)

- A wireless Inateck barcode scanner (exact model and keyboard layout unknown) is used to pick a book and to pick a pupil quickly.
- Record that pupil X borrowed book Y on date T.
- Add / remove / edit pupils. A pupil is identified by last name + first name.
- Generate a barcode for each book. Add books manually: title (only mandatory field), author, collection, publication date, ISBN.
- **Batch add**: several books (or N copies of a title) at once, generate their barcodes, print on an A4 sheet, tape onto the books.
- Barcodes are essential so that everything still works if the scanner dies: the code is printed in clear under each barcode and can be typed by hand.
- A view listing all books borrowed for more than a configurable period (default 3 weeks).
- Lists of books and pupils must filter instantly on every field as the user types (dynamic update).

## Decisions already made (do not re-litigate without a reason)

- **Rust + `eframe/egui`**: single .exe, no runtime, no WebView. Immediate mode makes live filtering trivial.
- **No database**: one JSON file `biblo.json` (hundreds of books and pupils, a few thousand loans per year). Atomic write (tmp file, fsync, rename). Daily backup in `backups/biblo-YYYY-MM-DD.json`, 30 kept. A corrupt file is never overwritten.
- **Barcodes: Code 128**, `L000123` for a book, `E000045` for a pupil (prefix + 6 digits). IDs are never reused. `L` and `E` are in the same place on QWERTY and AZERTY.
- The scanner acts as a keyboard (types the code + Enter): a scan field is always focused, the prefix routes the scan to book or pupil. Manual entry accepts `L123`, or `123` in a context where the type is known.
- **AZERTY fallback** is implemented in `codes.rs`: a US-layout scanner on an AZERTY Windows types `&é"'(-è_çà` instead of `1234567890`.
- **Printing**: A4 PDF opened in the default PDF viewer. Plan: write the PDF by hand with no extra crate (barcode bars are filled rectangles, text uses the built-in Helvetica font).
- Pupil cards with barcodes are generated by the app (pupils have none today). No "class" field: last name + first name only.
- **Return flow**: scanning an already-borrowed book proposes "Return".
- **Loan date**: strict date (dd/mm/yyyy), set automatically to today, manually editable to fix mistakes.
- **Publication date**: strict year only (4 digits, 1000 to 2200). Not confirmed with the user: they said "strict date"; I read it as year-only. Easy to change in `BookInput::cleaned` and `dates::parse_year`.
- **License: 0BSD** (user wants the most permissive possible).

Choices I made without explicit approval (mention them to the user if relevant):
- Books are **archived**, not deleted, like pupils; history is kept. Archiving is refused while on loan.
- Two non-archived pupils cannot have the same name (case-insensitive); archiving frees the name.
- "Overdue" means borrowed N days **or more** (`>=`); N = 0 lists every open loan.
- The daily backup is taken at the first app start of the day.

## Current state

**Milestone 0 is written but has NEVER been compiled or run**: the design session had no Rust toolchain. Nothing is verified yet.

Files: `Cargo.toml`, `LICENSE`, `.gitignore`, `src/{lib,error,codes,dates,library,store}.rs`. Deps: `serde`, `serde_json`, `chrono` (default features off; `clock`, `serde`, `std`). No `Cargo.lock` yet.

API sketch:
- `Library` (pure in-memory rules, every op validates before mutating): `add_book(s)/add_copies/update_book/archive_book`, `add_student/update_student/archive_student`, `lend/return_book/edit_loan/cancel_loan`, `open_loan_for_book`, `open_loans_by_book` (use this for the status column of a long list, one pass per frame), `overdue(today, min_days)`, `loans_of_book/loans_of_student`.
- `Store::open(dir, today)`, `store.apply(|lib| ...)` (mutates and saves), `store.lib()`, `store.backup_error()`.
- `codes::{book_code, student_code, parse_code, parse_code_or_number}`, `dates::{parse_date, format_date, parse_year}`, `today()`.

**First task: run `cargo test`, fix any compile or test failures, then `cargo clippy`, then commit `Cargo.lock`.**

## Remaining milestones

1. **Code 128 encoder + A4 PDF label sheets.** Implement the encoder from the standard pattern table, validate it against an independent implementation (e.g. a Python one, or a decode round-trip test in Rust). Tests: known checksum vectors, every symbol is 11 modules, stop pattern is 13. Label grid on plain A4 with thin cut lines (constants at the top of the file so the layout is easy to tweak; size not decided by the user, suggest 3 columns x 8 rows). Code in clear under each barcode. Pupil cards use the same machinery.
2. **GUI shell + Books, Pupils, Batch-add screens.** Live filtering on all fields, accent- and case-insensitive (write a small `fold()` helper: lowercase and strip French accents by hand, no extra crate). Book detail with loan history. Batch add: table of rows or "N copies of a title", then generate the sheet. Test on the real Windows PC early (see risks).
3. **Loan / Return screen** (home screen, scan field always focused). Scan pupil, then scan book: loan recorded today. Scan a borrowed book: propose return. Clear on-screen feedback after every scan (big, readable).
4. **Overdue screen**: threshold in days, default 21, editable. Show book, pupil, date, days out.
5. **Release**: `cargo build --release`, README (usage, troubleshooting, restoring a backup, scanner layout tips), LICENSE already present.

## Risks and notes

- **OpenGL on an old PC without a graphics driver**: the window may fail to open with the default `glow` backend. Fallback: switch `eframe` to `wgpu` (DirectX). Test on the target PC at milestone 2.
- **Static C runtime** so the .exe needs no VC++ redistributable: for the MSVC target add `rustflags = ["-C", "target-feature=+crt-static"]` in `.cargo/config.toml`. Decide at milestone 5.
- **Cross-compiling from Ubuntu**: `rustup target add x86_64-pc-windows-gnu` + `sudo apt install mingw-w64` + `cargo build --release --target x86_64-pc-windows-gnu`. Always validate on the real Windows PC. Use `#![windows_subsystem = "windows"]` to avoid a console window.
- **Ubuntu build deps for eframe** (confirm at milestone 2): `build-essential pkg-config libxkbcommon-dev libwayland-dev libx11-dev libxcb-render0-dev libxcb-shape0-dev libxcb-xfixes0-dev libgl1-mesa-dev`.
- Opening a PDF: `cmd /C start` on Windows, `xdg-open` on Linux (use `cfg`). Data directory: next to the executable on both OSes (not Program Files, which is not writable).
- Two simultaneous app instances would overwrite each other (last write wins). Not handled; consider a lock file.
- Scanner model and layout are unknown. If scans arrive garbled on the real PC, check `parse_code` normalization first, then the scanner's keyboard-layout setting.
- Pin versions through `Cargo.lock` (commit it); keep the dependency list minimal.

## Working agreements

Keep it simple. No dependency without a clear reason. Run `cargo test` (and `cargo clippy`) before saying something works. Do not change the scope or the decisions above silently: tell the user.
